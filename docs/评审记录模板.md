# vX.Y 评审记录模板

> **用途**: 每版交付后, 评审方对「开发计划 + 开发交付 + 实际 git 树」三者对账, 产出
> `vX.Y评审记录__<slug>.md`。本模板即该文件的骨架 —— 复制后逐节填写, 不留空节。
>
> **为什么有这个载体** (v2.5 P0-4): 本仓 v1.x~v2.4 十五个版本从未产出过评审记录
> (`find` + `git log --all --name-only` 双查为空), 导致各版遗留项只能散落在交付文档
> §5/§8 与实机记录中, 靠下一版计划起草时人工回收 —— v2.5 的 CO-1…CO-11 就是这么
> 拼出来的。本模板把该环节固定下来: **没有评审记录, 下一版计划就无输入可依**。

---

## 0. 元信息

| 字段 | 值 |
|---|---|
| 被评审版本 | vX.Y |
| 交付 commit | `<hash>`(=`tag vX.Y`) |
| 被评审文档 | `vX.Y开发计划__<slug>.md`、`vX.Y开发交付__<slug>.md` |
| 基线(回滚点) | `tag vX.Y-start` = `<hash>` |
| 评审日期 | YYYY-MM-DD |
| 评审结论 | 通过 / 有条件通过 / 不通过 |

## 1. 核验方法与范围

写明本次核验**实际执行**的手段与边界(哪些用 `git diff` 逐行核, 哪些只做了抽样),
以及**未能核验**的部分与原因 —— 未核验项不得默认为通过。

## 2. 硬性约束(HC-n)逐条核验

计划 §2 的每条 HC 一行结论 + 证据(命令与输出要点)。违反任一条即交付不合格。

| HC | 结论 | 证据 |
|---|---|---|
| HC-1 | 通过/不通过 | `sh tools/apidump.sh --diff` 输出… |

## 3. 验收标准(AC-n)逐条核验

计划 §4 的每条 AC 一行结论 + 证据。**声称必须经得起 `git diff` 核验**。

## 4. 偏差记录核验

对交付文档 §3 的每一处偏差: 是否成立、理由是否充分、影响是否如实。

## 5. CO 编号规则

**CO = Carry-Over(遗留项/整改项)**, 是评审记录与下一版计划之间的**唯一交接编号**。

- **编号格式**: `CO-<十进制序号>`, 从 `CO-1` 起, **在同一版本的评审记录内唯一且连续**;
- **编号归属**: CO 号一经分配即与该版本绑定, 后续版本引用时写全 `CO-n(vX.Y)`;
- **分配时机**: 评审时对"交付文档 §5 未完成项 / §6 遗留风险 / 本记录 §6 新发现问题 /
  §2-§3 的**不通过项**"逐条编号 —— **不得留白**: 每条未通过项与新发现问题都必须有 CO 号;
- **去向**: 每条 CO 必须在下一版计划的 §1.1「CO 逐条处置表」中被**逐条处置**
  (见下节四选项), 未出现在下版计划中的 CO 视为**丢失**, 属评审不通过项;
- **跨版延续**: 上一版"暂缓/拒绝"的 CO 若触发条件仍未满足, 下一版须**重新声明一次**
  处置结论(可写"维持暂缓"), 不得静默消失。

### 5.1 处置字段(下一版计划 §1.1 逐条填)

| 字段 | 取值 | 含义 |
|---|---|---|
| **处置** | **纳入** | 本版实现, 必须落到具体任务号(Pn-m) |
| | **暂缓** | 本期不做, **必须给出触发条件**(条件未触发即不消耗版本容量) |
| | **拒绝** | 不做且不再排队, **必须给出理由**; 若属库级原则性拒绝, 同步写入 API_GUIDE/候选池 |
| | **已关闭** | 已在前轮完成/已被其它工作覆盖, 附关闭证据 |
| **来源** | — | 上一版评审记录的 CO 号, 或交付文档/实机记录的章节号 |
| **理由 / 触发条件** | — | 四选项均**必填**(「纳入」填落点, 其余填条件或理由) |

### 5.2 与计划的互引(双向)

- 评审记录 → 计划: 每条 CO 必须在计划 §1.1 表中有对应行;
- 计划 → 评审记录: 计划 §1 须声明**输入来源** —— 上一版评审记录文件名, 或
  「**上一版评审记录不存在**」的显式声明(不得静默跳过);
- 交付文档 → 评审记录: 交付文档须引用本版评审记录, 或显式声明其缺失;
- 机检: `tools/docsync.sh` 断言「当前版本交付文档引用评审记录或声明缺失」。

## 6. 新发现问题(本记录对下一版的输入)

评审过程中发现、但计划与交付文档均未记载的问题。逐条给 CO 号。

| CO | 问题 | 严重度 | 建议处置 |
|---|---|---|---|
| CO-1 | | 高/中/低 | |

## 7. 遗留风险复评

对交付文档 §6 的每条遗留风险: 是否仍成立、是否新增。

## 8. 结论与放行

- 是否满足发布条件(HC 全过 + AC 全过, 或列出豁免项与豁免依据);
- 下一版计划的**必含项**(带 CO 号的硬性输入)。

---

> 填写纪律: **每节都必须有实质内容**; 不适用写"不适用 + 原因", 不留空。
> 结论行只写"通过/不通过", 理由写在证据列 —— 让复核者能独立重跑命令得到同一结论。
