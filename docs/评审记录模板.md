# vX.Y 评审记录模板

> **用途**: 每版交付后, 评审方对「开发计划 + 开发交付 + 实际 git 树」三者对账, 产出
> `vX.Y评审记录__<slug>.md`。本模板即该文件的骨架 —— 复制后逐节填写, 不留空节。
>
> **为什么有这个载体** (v2.5 P0-4): 本仓 v1.x~v2.4 十五个版本从未产出过评审记录
> (`find` + `git log --all --name-only` 双查为空), 导致各版遗留项只能散落在交付文档
> §5/§8 与实机记录中, 靠下一版计划起草时人工回收 —— v2.5 的 CO-1…CO-11 就是这么
> 拼出来的。本模板把该环节固定下来: **没有评审记录, 下一版计划就无输入可依**。

## 1. 核验方法与范围

写明本次核验**实际执行**的手段与边界(哪些用 `git diff` 逐行核, 哪些只做了抽样),
以及**未能核验**的部分与原因 —— 未核验项不得默认为通过。

**docref 红输出判读先看失败阶段(v2.16 G0-2 固化, `CO-1(v2.15)`; 沿 v2.15 交付 §6 口径)**:"修订登记含无效 SHA(越界)"类红 = **登记提取碰撞形态**(inline-code 引用行被误捕获——v2.14 文档转红为首个实例, token 为该文档自身版本链、位于记录终点之前), **不等于**"未登记实质变更"红; 判读顺序 = 失败阶段 → 越界 token 归属 → 实质变更核对。

**碰撞规避写作纪律(v2.17 G0-1 增补, `CO-2(v2.16)`; v2.18 注: 根治已实施——提取收紧为 @ 前缀形态, 本条降为纵深防御/提示性惯例)**: 本记录及一切引用遵守三形态——含"修订登记"短语的散文行**不携带提交 token** / 引用红原文**一律入围栏** / 短语行与 token 行**分行书写**; 四实例链与评估记录见 `docs/proposals/docref_collision_assessment.md`(排期 v2.18, 待评审批准)。

**按值声明口径与机械抽检(v2.18 G0-1 增补, `CO-1(v2.17)`)**: 计数判据的**每个值**须按值标注口径(行计数/出现次数), 表首行总声明不得替代逐值标注; 复核侧对 **≥2 的声称值抽一条复跑 `grep -c` 对账**(机械抽检, 命令与输出入记录)。反例: v2.17 交付 §2 表两值("围栏=2/基线滚动=2")为次数口径而行计数各=1——纪律在位而自检失效。**时点括注校准与仓库状态类声称收口(v2.18 G0-1 增补, `CO-2(v2.17)`; v2.19 G0-2 收口, `CO-1(v2.18)`)**: 时点括注须与所引数值的实际测量时点一致(不得以"前"指"后"态); **复核侧对涉及仓库状态(文件计数/存在性/diff 判定/门读数)的声称, 须核其终态复测值或明示测量时点**(同族四实例: v2.10 未触发回刷 / v2.11 G0 窗口为空 / v2.14–v2.17 口径与时点 / v2.18 AC-2(f) 计数终态失准)。
**定稿后终态复测(v2.20 G0-2 增补, `CO-3(v2.19)`)**: 交付文档定稿(登记行合并)后、打 tag 前, 对全部仓库状态类声称**复跑一次并留痕**(§7.4 第⑧行: 复跑命令/输出/时点); **定稿提交后不得再改可观测数值**(失准走勘误批)。评审侧核验 ⑧ 留痕形态(复跑命令/输出/时点齐备)。 **复跑清单 = 封闭枚举(v2.21 G0-2 增补, `CO-5`/`CO-7(v2.20)`)**——四类封闭清单缺一不复算即违 ⑧: (a) §2 全部仓库状态类值 / (b) §4 diffstat 三数 / (c) G0 窗口在最终右端 / (d) 登记链放行判定; 分段形态(tag 符号终点在 tag 前结构性不可测)裁定 = 接受, 前置段清单必须封闭。 **取值口径与命令原文(v2.22 G0-3 增补, `CO-6(v2.21)` 脚本化实施)**: (b) 类取值口径 = **全量含本文档**(与 §4 一致), 自排除口径(`-- ':(exclude)v<主.次>开发交付__*.md'`)为辅助口径**须并列输出**; (d) 类留痕 = **逐文档判定清单**(聚合行废止)。**取值命令原文 = `sh tools/gatecheck.sh <主.次>`**((b)/(d)/(a) 全局项机读; (c) 与版本特有项人工执行并对账); 评审侧核验 §7.4⑧ 行引用 gatecheck 输出而非人工誊抄。

## 3. 验收标准(AC-n)逐条核验

计划 §4 的每条 AC 一行结论 + 证据。**声称必须经得起 `git diff` 核验**。

### 3.1 AC ↔ 冻结 API 形状互洽(复核项, v2.6 P0-4 起)

除逐条核验外, 还须复核**每条 AC 的断言对象与计划 §3 声明的 API 形状能否同时成立**
(返回值/字段/字节输出 vs 签名)——这是 `CO-12(v2.5)` 第④项的评审侧复核:

- 断言对象与形状**冲突** → 属计划缺陷, 记 CO(即使交付已用纯追加等方式化解);
- 冲突已由交付期以**纯追加**化解 → 记入偏差表并确认 `apidump --diff` 无删改;
- 触碰既有签名 → 属破坏性变更, 应进 `docs/v3-candidates.md` 而非本版。

> 反例(v2.5): 计划冻结的 `result(m,&qty)` 返回单值, 与该版 AC"读回值逐值相等"
> 无法同时成立 → 交付期被迫追加 `_data()`。若起草/评审任一侧做过本项复核,
> 该缺陷可在开发前消除。

### 3.2 基线滚动复核项(v2.8 P0-4 起, `CO-2(v2.7)` 评审侧闭环)

除逐条核验外, 还须复核**模板 §7 第⑥项(基线滚动)的执行面**:

- 本版交付是否按计划**显式列出的三件事**执行: 归档本版 API 清单(worktree 真生成 +
  sha256) / `apidump` 默认基线切至本版归档 / docsync 基线断言同批;
- 归档件与上一版归档的差异是否**逐行列出**且限于版本宏行(超出即公开面未登记变化);
- 上一版的基线是否在上一版**发版点**已滚动(滞留跨版即计 CO, 如 v2.6/v2.7 连续滞留)。

## 5. CO 编号规则

**CO = Carry-Over(遗留项/整改项)**, 是评审记录与下一版计划之间的**唯一交接编号**。

- **编号格式**: `CO-<十进制序号>`, 从 `CO-1` 起, **在同一版本的评审记录内唯一且连续**;
- **编号归属**: CO 号一经分配即与该版本绑定, 后续版本引用时写全 `CO-n(vX.Y)`;
- **分配时机**: 评审时对"交付文档 §5 未完成项 / §6 遗留风险 / 本记录 §6 新发现问题 /
  §2-§3 的**不通过项**"逐条编号 —— **不得留白**: 每条未通过项与新发现问题都必须有 CO 号;
- **去向**: 每条 CO 必须在下一版计划的 §1.1「CO 逐条处置表」中被**逐条处置**
  (见下节四选项), 未出现在下版计划中的 CO 视为**丢失**, 属评审不通过项;
- **跨版延续**: 上一版"暂缓/拒绝"的 CO 若触发条件仍未满足, 下一版须**重新声明一次**
  处置结论(可写"维持暂缓"), 不得静默消失。

### 5.1 处置字段(下一版计划 §1.1 逐条填)

| 字段 | 取值 | 含义 |
|---|---|---|
| **处置** | **纳入** | 本版实现, 必须落到具体任务号(Pn-m) |
| | **暂缓** | 本期不做, **必须给出触发条件**(条件未触发即不消耗版本容量) |
| | **拒绝** | 不做且不再排队, **必须给出理由**; 若属库级原则性拒绝, 同步写入 API_GUIDE/候选池 |
| | **已关闭** | 已在前轮完成/已被其它工作覆盖, 附关闭证据 |
| **来源** | — | 上一版评审记录的 CO 号, 或交付文档/实机记录的章节号 |
| **理由 / 触发条件** | — | 四选项均**必填**(「纳入」填落点, 其余填条件或理由) |

### 5.2 与计划的互引(双向)

- 评审记录 → 计划: 每条 CO 必须在计划 §1.1 表中有对应行;
- 计划 → 评审记录: 计划 §1 须声明**输入来源** —— 上一版评审记录文件名, 或
  「**上一版评审记录不存在**」的显式声明(不得静默跳过);
- 交付文档 → 评审记录: 交付文档须引用本版评审记录, 或显式声明其缺失;
- 机检: `tools/docsync.sh` 断言「当前版本交付文档引用评审记录或声明缺失」。

**证据表述纪律（v2.11 G0-2 增补, `CO-2(v2.10)`）**: 零命中/提取类机械判据的**判据串必须不匹配判据行自身**（如以"全文件 diff"限定替代裸"全文件"），或在判据行**显式声明"排除本行"**并以排除后口径声称; **时点性声称必须带时点限定**（读数实测时点 ≠ 终态时点须写明）; 引证文件落笔前 `ls` 自查存在性。本记录对被评对象的读数一律记录**实测时点**。

> 填写纪律: **每节都必须有实质内容**; 不适用写"不适用 + 原因", 不留空。
> 结论行只写"通过/不通过", 理由写在证据列 —— 让复核者能独立重跑命令得到同一结论。
