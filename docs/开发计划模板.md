# vX.Y 开发计划模板

> **用途**: 版开发启动前产出 `vX.Y开发计划__<slug>.md`（本文档即骨架，复制后逐节填写）。
> 计划一经交付即**冻结**，开发期不回改；范围变更直接修订并在文首"状态"行记日期。
>
> **为什么有这个载体**（v2.6 P0-4 / `CO-12(v2.5)`）: v2.5 计划出现三处**起草期可避免**的缺陷 ——
> ① 快照 tag 命名与 `release.yml` 的 `v*` 触发面冲突（且"无副作用"结论未实测即写入）；
> ② 板侧落点写成库内 `examples/`，实际挂载点在库外私有工程；
> ③ 缺"AC ↔ 冻结 API 形状"互洽检查（`result()` 单值 vs AC 要求"逐值相等"，交付期才发现）。
> 本模板把这些变成**起草期的强制自检**，详见 §7。

---

## 1. 目标与范围

### 1.1 输入说明与 CO 逐条处置

**输入来源必须显式声明**：上一版评审记录文件名（`vX.Y评审记录__<slug>.md`），或
"**上一版评审记录不存在**"的显式声明 —— 不得静默跳过（机检见 `tools/docsync.sh`）。

逐条处置上一版评审记录的全部 `CO-n(vX.Y)`：

| # | 问题摘要 | 来源 | 处置 | 理由 / 触发条件 |
|---|---|---|---|---|
| CO-1 | | AC-n / §n | 纳入 / 暂缓 / 拒绝 / 已关闭 | **四选项均必填**（处置字段定义见 `docs/评审记录模板.md` §5.1） |

### 1.2 本版做什么

编号列出交付项，每项一句话说清"做到什么程度"。

### 1.3 明确不做什么（Non-goals）

逐条列出边界（含历版永久边界重述），触发条件未满足的候选不进本版。

---

## 2. 硬性约束（违反任一条即交付不合格）

`HC-n` 编号，每条**可客观核验**，并写明核验命令/判据。至少覆盖：

- 契约零破坏（`apidump --diff` 的允许变更面）；
- 库不变式（零动态内存 / 多实例 / 分层依赖 / 不内部取时基 / 不新增开关）；
- 数字回刷同批（README / API_GUIDE / CHANGELOG / 体积表 / 交付文档）；
- 真机证据与 tag 完整性（走单证据须取自**不含下一版代码**的提交）；
- 如实性纪律（未做即声明；**不得声称本机已跑**本机跑不了的检查）。

---

## 3. 任务分解

任务号 `Pn-m`（P0/P1/P2…），每条含：描述 / 涉及文件（**写全路径**）/ 影响分析 / 优先级。
落点含**板侧**时，必须按 §7 第③项写库外私有全路径。

---

## 4. 验收标准

`AC-n` 编号，每条可客观核验、标注对应任务号。**每条都要能被评审方独立复跑**。
必含一条"全量回归"AC（用例数 / 示例 / 覆盖率 / 三个治理脚本 / CI）。

---

## 5. 可裁量项与不可偏离

- **可裁量**：开发者可自主决策的细节（实现取向、命名、章节位置…），逐条列出；
- **不可偏离**：§1.1 的 CO 处置结论、全部 HC、基线规则 —— 明确标注"不得偏离"。

---

## 6. 基线

| 字段 | 内容 |
|---|---|
| 首选基线 | `tag v<上一版>`（若该 tag 不存在则声明实际起点） |
| 快照（动手前必打） | `git tag snap-<ver>-start <起点 commit>`（**不带 `v` 前缀**，理由见 §7①） |
| 分支规则 | 库内改动在 `dev/v<ver>`；发版 tag 必须在下一版代码合入 `main` **之前**定着 |
| 顺序规则 | 板不可用时的合法路径（库内项先行 / 板到达后合流的先后与合流点） |
| 偏离申报 | 实际起点与上述不符时，须在交付文档首行声明 |

---

## 7. 起草期核验清单（本模板的存在理由，**六项全过才算起草完成**）

| # | 检查项 | 要求 | 反例（v2.5 实际发生） |
|---|---|---|---|
| ① | **内部 tag 命名** | 快照/内部 tag 一律 `snap-<ver>-start`（**不带 `v` 前缀**），并在计划中附"触发面"实测要求：打完快照后必须复核 `gh run list --limit 3` 无新 run、`gh release list` 无新增 —— **禁止**写"快照 tag 无副作用"这类未实测断言 | `v2.5-start` 匹配 `release.yml` 的 `tags: [v*]` → 触发 Release workflow（run `35378057777`，已 cancel，未产出 Release） |
| ② | **"无副作用/不会触发"类断言** | 起草期**逐条实测**（给命令与结果），未实测的此类断言不得写入计划 | 上一条同源：当时该结论未经实测即写入 |
| ③ | **板侧落点标注** | 板侧任何改动一律标注为**板侧工程私有文件（库外，不在本仓 git）**并写全路径（如 `D:\code\STM32CubeMX\...\Core\Src\et_demo.c`、同步目录 `...\Core\et\`）；**禁止**写成库内 `examples/` | P2-2 落点写成 `examples/stm32g474_demo.c`，而该文件从未含 Modbus 代码 |
| ④ | **AC ↔ 冻结 API 形状互洽** | 逐条核对：每条 AC 的断言对象（返回值/字段/字节输出）与 §3 声明的 API 形状**能否同时成立**；触碰形状者必须走纯追加或 v3 破坏性窗口 | `result(m,&qty)` 返回单值 vs AC"读回值逐值相等" → 交付期被迫追加 `_data()` |
| ⑤ | **证据落点章节号 + 占位节清理** | 每条 AC 的证据落点必须写**具体章节号**（不许写"见实机记录"这类无号指向）；落点若为**追加节**，须先用命令确认该节号未被占用（如 `grep -n '^## ' <文件>`），并**清理/标注被取代的旧占位节的承接关系**（"本节已由 §X 承接"） | v2.6 的 AC-1 指向 `移植stm32实机记录.md` **§12**，实际证据在 **§13**（§12 仍是"未执行的走单（如实挂账）"旧占位节）→ `CO-11(v2.6)` |
| ⑥ | **基线滚动**（v2.8 P0-4 新增；v2.9 G0-1 按 `CO-1(v2.8)` 澄清口径改写） | 每版计划必须**显式列出**基线滚动三件事：① **P0 期**归档**上一已发布 MINOR** 的 API 清单（`git worktree` 于**该版 tag** 真生成 + sha256 + 差异说明，禁止手工编辑）；② `tools/apidump.sh` 默认基线切至该归档（docsync 基线断言自证零字面量改动——v2.8 P3-4 起为单一来源动态断言，无需逐版改指）；③ **发版点**对本版清单 **0/0 复读**（`apidump --diff` 对默认基线，防发版窗口末刻漂移）。反例：v2.6/v2.7 **连续两版**未归档（v2.7 计划 HC-1 写"对 v2.6 基线"却无归档任务 → `CO-2(v2.7)`，基线滞留跨两版后由 v2.8 补归档清偿）；原口径（v2.8 P0-4 原文）"发版点归档本版 API 清单于当版 tag 真生成"属自引用不可执行（发版点时该 tag 尚不存在 → `CO-1(v2.8)`），本行即其改写 | v2.6/v2.7 计划均未列归档任务，`docs/API_INVENTORY_v2.6.md` 在 v2.7 发布后仍不存在（v2.8 起草期实测） |

**自检落点**：本清单六项须在计划文末"起草期合规声明"中逐项声明已执行（含实测命令与结果）。
评审记录 §1 核验方法亦须包含第④项的复核（见 `docs/评审记录模板.md` §3）。

---

- **证据表述纪律（v2.11 G0-2 增补，`CO-2(v2.10)`）**：零命中/提取类机械判据的**判据串必须不匹配判据行自身**（如以"全文件 diff"限定替代裸"全文件"），或在判据行**显式声明"排除本行"**并以排除后口径声称；**时点性声称必须带时点限定**（如"G0 窗口时点 OK；终态转红属设计行为"）；引证文件落笔前 `ls` 自查存在性。反例：v2.10 的 AC-9 判据行以裸"全文件"自命中 1 处、AC-1⑤ 时点性声称无时点（`CO-1/CO-2(v2.10)`）。
- **判据自洽性检查（v2.12 G0-2 增补，`CO-2(v2.11)`）**：① 判据涉"改 X 则为空/为 0"形态时，须核 X 的义务方是否在本版任务内——判据 vs 任务冲突即计划缺陷（反例：v2.11 AC-1 要求 G0 窗口 docs diff 为空，而同版 G0-2 必改两模板，任何时点不可满足）；② 预置数值须**逐项代入复算**，公式优先于抄数值（反例：v2.11 CO-3 预置 312 与自身推导 313 矛盾）。
- **判据区间右端核对形态（v2.14 G0-1 增补，`CO-1(v2.13)`——第四代根治）**：判据区间右端为 `HEAD`/tag 时，须对账本版任务是否触碰同路径；触碰则右端**时点化**（写作"G0 窗口终态提交（SHA 实测回填）"）并在判据内**显式写出终态对照值**（防"非空即缺陷"误读）。两代同源反例：v2.11 AC-1（docs 型——判据要求 docs 为空而同版 G0-2 必改两模板）、v2.13 AC-1（库面/门型——判据区间 `..HEAD` 而 P0-1/P0-2 触碰 `et_config.h`/`tools/apidump.sh`，终态必非空）。
- **HC-4 自检行③ sanctioned 措辞（v2.13 G0-2 增补，`CO-1(v2.12)`）**：交付文档 §7.4 自检表行③的成立理由只允许两形态机制之一——"判据作用域不含文档自身"或"显式排除本行"声明；**禁以引号包裹为理由**（引号不改变 grep 匹配，非机制——`CO-3(v2.11)` 已判定；v2.11→v2.12 该行理由已跨两代复制，第四代起按本条预置口径书写，禁再照抄无效描述）。
- **P2-1 惯例措辞——版本链断言与涉及文件清单（v2.13 G0-2 增补，`CO-2(v2.12)`；v2.14 G0-2 增补，`CO-2(v2.13)`）**：计划 P2-1 描述 docsync 版本链断言任务时统一为"**动态循环自动扩展；如需字面量改动则偏差登记**"，不写"docsync.sh 版本链断言增 X 节"式字面量改动句——v2.11/v2.12 两版范围内 docsync.sh 实际零 diff，计数增长由动态循环承载，"涉及文件列了但零改动"构成表里差。
  数字回刷任务的"涉及文件"须**列全门强制面**——常设两项 = ① `docs/API_INVENTORY.md` **工作清单重生成**（docbuild/docsync 强制）；② README **基线名前滚**（docsync 基线名交叉断言强制）；并在判据自洽性检查中一并核对"**门强制面 ⊆ 计划清单**"。依据：v2.12 清单列全 / v2.13 漏列两项——两版均被 docsync 断言强制并走偏差登记。
- **计数记法与命令一致（v2.15 G0-1 增补，`CO-1(v2.14)`）**：计数类判据须**声明口径**——行计数用 `grep -c`（命中行数）、出现次数用 `grep -o | wc -l`，同一判据内两口径不得混用。反例：v2.14 AC-2 声称 `grep -c … = 2` 实为出现次数口径、行计数 = 1——数值真实、语义成立、记法与命令不符。
- **碰撞规避写作纪律（v2.17 G0-1 增补，`CO-2(v2.16)`——登记提取碰撞面四实例链，评估记录见 `docs/proposals/docref_collision_assessment.md`）**：三形态任选其一或叠加——① 含"修订登记"短语的散文行**不携带提交 token**（token 落于相邻行/表行）；② 引用 docref 红原文等敏感内容**一律入围栏**（围栏行被登记提取排除）；③ 短语行与 token 行**分行书写**。依据：v2.16 交付实证有效（四实例 = v2.10 证据行 / v2.14 转红引用行 / v2.15 同路径 / v2.15 文档否定语境自述行）。

> 填写纪律：每条 HC/AC 必须可被评审方独立复跑；"暂缓/拒绝"必须附触发条件或理由；
> 板侧与库内落点分开写；数字类声明一律给出复现命令。
