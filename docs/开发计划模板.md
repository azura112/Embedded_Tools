# vX.Y 开发计划模板

> **用途**: 版开发启动前产出 `vX.Y开发计划__<slug>.md`（本文档即骨架，复制后逐节填写）。
> 计划一经交付即**冻结**，开发期不回改；范围变更直接修订并在文首"状态"行记日期。
>
> **为什么有这个载体**（v2.6 P0-4 / `CO-12(v2.5)`）: v2.5 计划出现三处**起草期可避免**的缺陷 ——
> ① 快照 tag 命名与 `release.yml` 的 `v*` 触发面冲突（且"无副作用"结论未实测即写入）；
> ② 板侧落点写成库内 `examples/`，实际挂载点在库外私有工程；
> ③ 缺"AC ↔ 冻结 API 形状"互洽检查（`result()` 单值 vs AC 要求"逐值相等"，交付期才发现）。
> 本模板把这些变成**起草期的强制自检**，详见 §7。

---

## 1. 目标与范围

### 1.1 输入说明与 CO 逐条处置

**输入来源必须显式声明**：上一版评审记录文件名（`vX.Y评审记录__<slug>.md`），或
"**上一版评审记录不存在**"的显式声明 —— 不得静默跳过（机检见 `tools/docsync.sh`）。

逐条处置上一版评审记录的全部 `CO-n(vX.Y)`：

| # | 问题摘要 | 来源 | 处置 | 理由 / 触发条件 |
|---|---|---|---|---|
| CO-1 | | AC-n / §n | 纳入 / 暂缓 / 拒绝 / 已关闭 | **四选项均必填**（处置字段定义见 `docs/评审记录模板.md` §5.1） |

### 1.2 本版做什么

编号列出交付项，每项一句话说清"做到什么程度"。

### 1.3 明确不做什么（Non-goals）

逐条列出边界（含历版永久边界重述），触发条件未满足的候选不进本版。

---

## 2. 硬性约束（违反任一条即交付不合格）

`HC-n` 编号，每条**可客观核验**，并写明核验命令/判据。至少覆盖：

- 契约零破坏（`apidump --diff` 的允许变更面）；
- 库不变式（零动态内存 / 多实例 / 分层依赖 / 不内部取时基 / 不新增开关）；
- 数字回刷同批（README / API_GUIDE / CHANGELOG / 体积表 / 交付文档）；
- 真机证据与 tag 完整性（走单证据须取自**不含下一版代码**的提交）；
- 如实性纪律（未做即声明；**不得声称本机已跑**本机跑不了的检查）。

---

## 3. 任务分解

任务号 `Pn-m`（P0/P1/P2…），每条含：描述 / 涉及文件（**写全路径**）/ 影响分析 / 优先级。
落点含**板侧**时，必须按 §7 第③项写库外私有全路径。

---

## 4. 验收标准

`AC-n` 编号，每条可客观核验、标注对应任务号。**每条都要能被评审方独立复跑**。
必含一条"全量回归"AC（用例数 / 示例 / 覆盖率 / 三个治理脚本 / CI）。

---

## 5. 可裁量项与不可偏离

- **可裁量**：开发者可自主决策的细节（实现取向、命名、章节位置…），逐条列出；
- **不可偏离**：§1.1 的 CO 处置结论、全部 HC、基线规则 —— 明确标注"不得偏离"。

---

## 6. 基线

| 字段 | 内容 |
|---|---|
| 首选基线 | `tag v<上一版>`（若该 tag 不存在则声明实际起点） |
| 快照（动手前必打） | `git tag snap-<ver>-start <起点 commit>`（**不带 `v` 前缀**，理由见 §7①） |
| 分支规则 | 库内改动在 `dev/v<ver>`；发版 tag 必须在下一版代码合入 `main` **之前**定着 |
| 顺序规则 | 板不可用时的合法路径（库内项先行 / 板到达后合流的先后与合流点） |
| 偏离申报 | 实际起点与上述不符时，须在交付文档首行声明 |

---

## 7. 起草期核验清单（本模板的存在理由，**六项全过才算起草完成**）

| # | 检查项 | 要求 | 反例（v2.5 实际发生） |
|---|---|---|---|
| ① | **内部 tag 命名** | 快照/内部 tag 一律 `snap-<ver>-start`（**不带 `v` 前缀**），并在计划中附"触发面"实测要求：打完快照后必须复核 `gh run list --limit 3` 无新 run、`gh release list` 无新增 —— **禁止**写"快照 tag 无副作用"这类未实测断言 | `v2.5-start` 匹配 `release.yml` 的 `tags: [v*]` → 触发 Release workflow（run `35378057777`，已 cancel，未产出 Release） |
| ② | **"无副作用/不会触发"类断言** | 起草期**逐条实测**（给命令与结果），未实测的此类断言不得写入计划 | 上一条同源：当时该结论未经实测即写入 |
| ③ | **板侧落点标注** | 板侧任何改动一律标注为**板侧工程私有文件（库外，不在本仓 git）**并写全路径（如 `D:\code\STM32CubeMX\...\Core\Src\et_demo.c`、同步目录 `...\Core\et\`）；**禁止**写成库内 `examples/` | P2-2 落点写成 `examples/stm32g474_demo.c`，而该文件从未含 Modbus 代码 |
| ④ | **AC ↔ 冻结 API 形状互洽** | 逐条核对：每条 AC 的断言对象（返回值/字段/字节输出）与 §3 声明的 API 形状**能否同时成立**；触碰形状者必须走纯追加或 v3 破坏性窗口 | `result(m,&qty)` 返回单值 vs AC"读回值逐值相等" → 交付期被迫追加 `_data()` |
| ⑤ | **证据落点章节号 + 占位节清理** | 每条 AC 的证据落点必须写**具体章节号**（不许写"见实机记录"这类无号指向）；落点若为**追加节**，须先用命令确认该节号未被占用（如 `grep -n '^## ' <文件>`），并**清理/标注被取代的旧占位节的承接关系**（"本节已由 §X 承接"） | v2.6 的 AC-1 指向 `移植stm32实机记录.md` **§12**，实际证据在 **§13**（§12 仍是"未执行的走单（如实挂账）"旧占位节）→ `CO-11(v2.6)` |
| ⑥ | **基线滚动**（v2.8 P0-4 新增，`CO-2(v2.7)` 根因根治） | 每版计划必须**显式列出**基线滚动三件事：① 发版点归档本版 API 清单（`git worktree` 于本版 tag 真生成 + sha256 + 差异说明，禁止手工编辑）；② `tools/apidump.sh` 默认基线切至本版归档；③ `tools/docsync.sh` 基线断言同批改指。反例：v2.6/v2.7 **连续两版**未归档（v2.7 计划 HC-1 写"对 v2.6 基线"却无归档任务 → `CO-2(v2.7)`，基线滞留跨两版后由 v2.8 补归档清偿） | v2.6/v2.7 计划均未列归档任务，`docs/API_INVENTORY_v2.6.md` 在 v2.7 发布后仍不存在（v2.8 起草期实测） |

**自检落点**：本清单六项须在计划文末"起草期合规声明"中逐项声明已执行（含实测命令与结果）。
评审记录 §1 核验方法亦须包含第④项的复核（见 `docs/评审记录模板.md` §3）。

---

> 填写纪律：每条 HC/AC 必须可被评审方独立复跑；"暂缓/拒绝"必须附触发条件或理由；
> 板侧与库内落点分开写；数字类声明一律给出复现命令。
